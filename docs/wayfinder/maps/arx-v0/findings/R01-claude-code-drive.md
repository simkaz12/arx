# R01 — driving Claude Code from Rust with a CanUseTool callback

**Date:** 2026-08-30. **Sources:** `code.claude.com/docs/en/{cli-reference,headless,hooks,model-config,sdk/sdk-typescript,sdk/sdk-python,sdk/sdk-permissions,mcp}` (fetched live); local `claude --version` → `2.1.240 (Claude Code)`; `claude -p --help` (same binary); npm registry `@anthropic-ai/claude-code@2.1.251`, `@anthropic-ai/claude-agent-sdk@0.3.251` (not installed locally, versions checked only). Tabularium decisions read: `e652ce3a`, `96d1ad3a`, `e4510547`, `68c366dc`, `ce46b9ea`, `64c789d0`, `0bd4df2f`, `5e8da52e`.

## Candidate 1 — `claude -p ... --permission-prompt-tool <mcp tool>`

**Mechanism.** `--permission-prompt-tool` names an MCP tool; Claude Code waits up to `MCP_TIMEOUT` (30s default) for that tool's MCP server to connect before the first turn, then routes any permission check that falls through the rule table to it (docs, cli-reference `--permission-prompt-tool`). Live-tested: the installed 2.1.240 CLI accepts the flag without an "unrecognized option" error, though it is **absent from local `--help` output** despite being documented — a listing gap, not a functional block, but unverified further (see Open).

- **(a) autocompact off** — no boolean disable exists in current docs. `--autocompact <auto|tokens>` sets a 100K–1M window (cli-reference); `CLAUDE_CODE_AUTO_COMPACT_WINDOW` is the equivalent env var (model-config). Sonnet 5 defaults to a 1M window with auto-compact at ~967K tokens. The lever is "push the window to the ceiling," not "turn it off."
- **(b) per-message usage** — yes. `SDKAssistantMessage.message` is a `BetaMessage` from the Anthropic SDK "includes fields like id, content, model, stop_reason, and usage" (sdk-typescript); this is the same envelope `--output-format stream-json` emits, confirmed by `--include-partial-messages` streaming docs (headless).
- **(c) built-ins stripped, MCP kept** — `--tools ""` disables "the built-in set" only (`claude -p --help`); MCP tools are a separate namespace, unaffected.
- **(d) system prompt replaced** — `--system-prompt <prompt>` sets the session's prompt outright (cli-reference notes `--exclude-dynamic-system-prompt-sections` is "ignored when `--system-prompt` ... is set," confirming replacement, not append).
- **(e) CLAUDE.md suppressed** — `--setting-sources` (comma list of `user,project,local`) controls this at the CLI; the SDK page states plainly that omitting `"project"` stops CLAUDE.md loading (sdk-typescript, "Default behavior"), and the CLI flag is the same underlying option — not separately re-stated for the CLI, so inferred rather than directly quoted for this exact surface.
- **(f) interrupt** — SIGINT ends the in-flight turn cleanly (headless: "send SIGINT ... before you stop the process").
- **(g) kill + fresh respawn** — `--session-id <uuid>` with no `--resume`/`--continue` starts fresh; `--no-session-persistence` guarantees no resumable artifact (cli-reference).

**Loses:** an MCP tool flagged `_meta["anthropic/requiresUserInteraction"]` can never be approved through this tool — "Claude Code converts an allow result for one to a deny" (headless) — a narrow, real gap. Also loses the SDK's richer per-call metadata (toolUseID, agentID, requestId, blockedPath) that `canUseTool` carries; the MCP tool receives only what MCP's schema lets it carry, and needs a live MCP server (handshake + 30s connect budget), not a fire-and-forget call.

## Candidate 2 — SDK sidecar (Node/Python)

**Mechanism.** `canUseTool`/`can_use_tool` is an in-process callback, invoked "only when the permission flow falls through to a prompt" (sdk-permissions), receiving `toolName, input, {signal, suggestions, blockedPath, decisionReason, toolUseID, agentID, requestId}` and returning a `PermissionResult`. Both TS and Python `ClaudeAgentOptions` expose it directly alongside a separate `permission_prompt_tool_name` field — the SDK supports both mechanisms, confirming they are genuinely distinct routes, not aliases.

- **(a), (b), (d)–(g):** identical to Candidate 1's findings — same CLI-level levers underlie both (`--autocompact`, stream-json's `usage`, `systemPrompt` string replacing the preset outright with default = "minimal prompt," `settingSources: []` explicitly documented to stop CLAUDE.md loading, `Query.interrupt()` plus SIGINT, fresh session by omitting resume options).
- **(c) corrected (L1-05 live probe, 2026-09-02):** `disallowedTools: ['*']` is not equivalent to Candidate 1's `--tools ""` — it also blocks the SDK's own `mcpServers`-provided tools before `canUseTool` ever runs, caught live when main was refused `mcp__arx__arx_ping` with zero gate crossing. The working strip is `tools: []`, the SDK's dedicated "disable all built-in tools" option, which leaves mounted tools admitted.

**Loses:** an entire process class arx must own — spawn, health-check, restart-on-crash, and bridge (stdout JSON or an RPC) — plus a second language runtime in the deployment. Gains the richest per-call context and a stable, versioned, typed interface instead of a raw wire protocol.

## Candidate 3 — PreToolUse hook, reframed as arx-owned (not injected into a foreign body)

**Mechanism.** Hooks run **first** in the evaluation order, ahead of deny/ask rules and `canUseTool` (sdk-permissions: "Run hooks first"). A `PreToolUse` hook handler returns `hookSpecificOutput.permissionDecision`: `allow | deny | ask | defer`, plus `permissionDecisionReason`. Critically, `"allow"` **does** skip the prompt for ordinary tools (hooks reference, "PreToolUse decision control" table) — it is a full grant, not a veto-only signal; "deny" blocks with the reason shown to the model. Handler types include `command` (shell subprocess, JSON stdin/stdout) **and `http`** ("send the event's JSON input as an HTTP POST request to a URL... the endpoint communicates results back through the response body using the same JSON output format," hooks reference) — arx can run a plain HTTP server and register it as the handler, no MCP handshake, no sidecar, no SDK.

**Ownership vs. mechanism (the R01 question on `96d1ad3a`).** That decision's rejection — "a second gate inside a body arx does not own" — is scoped explicitly to a **hand's** body: a foreign Claude Code loop whose own `.claude/settings.json`/config surface arx would have to reach into. The mechanism itself is not what was rejected; primary sources confirm hooks can deliver a complete allow/deny+note verdict per call. For **main**, arx owns the spawn outright (its own `--settings`, its own directory) — the ownership objection does not transfer. This is a mechanism candidate 96d1ad3a never ruled on for main, and D06's own resolution text — "the gate speaks Claude Code's PreToolUse hook contract" — is consistent with treating the hook JSON shape as at least a reusable envelope, though the same resolution and `e652ce3a` both name `CanUseTool` as main's actual wiring, so this reading needs the owner's confirmation, not mine.

- **(a),(b),(d),(f),(g):** identical to Candidate 1 — session/CLI-level, orthogonal to which permission mechanism is wired in.
- **(c):** identical — `--tools ""` plus mounted MCP servers.
- **(e):** `--bare` strips hook auto-discovery along with CLAUDE.md, but its own doc lists `--settings` as one of the channels still honored under `--bare` ("Explicitly provide context via: ... `--settings` ...", `claude -p --help`), so `--bare --settings <hooks.json>` should compose fast-start-without-CLAUDE.md with an explicit hook — plausible from the flag's own text, not separately demonstrated end-to-end.

**Loses:** same `requiresUserInteraction` restriction as Candidate 1 ("a hook can't skip its approval prompt with allow ... because Claude Code can't confirm the hook collected the interaction the tool needs," hooks reference). A hook returning `"ask"` surfaces Claude Code's own interactive terminal prompt, which does not exist headless — so arx's handler must resolve any suspend-for-operator itself and always return a final `allow`/`deny`, never delegate "ask" to Claude Code.

## Recommendation

Standing decisions `e652ce3a` and `0bd4df2f` already fix main's drive surface to the Agent SDK, and Candidate 2 gives the richest, most stable per-call contract for the gate — that stays the safer route for B04 as scoped. But this research surfaces a materially cheaper alternative the design never evaluated: Candidate 3, wired as an HTTP hook handler arx owns directly, delivers the same allow/deny+note verdict per call, ahead of Claude Code's own rule evaluation, using nothing beyond an HTTP server in Rust — no sidecar, no second runtime, no MCP handshake. Worth a design reopen if B04's sidecar-supervision cost turns out heavier than expected; not something to substitute quietly since `e652ce3a`/`64c789d0` are in force.

## Open

Whether the `control_request`/`control_response` envelope underlying `canUseTool` (hinted by sdk-typescript's "A control_response your application sends outside the SDK... echoing requestId") is a stable, documented wire protocol a Rust process could speak directly against plain CLI stdio — no dedicated spec page found, unconfirmed. Whether `--setting-sources` excluding `project` suppresses CLAUDE.md at the CLI the same way `settingSources: []` does in the SDK — documented for the SDK, not separately re-stated for the flag. Whether `--mcp-config` still loads under `--bare` (the doc names it among bare-compatible explicit overrides but doesn't confirm for the hook-handler-as-MCP-tool case specifically). `e4510547`'s `autoCompactEnabled: false` names a field absent from every current options table checked (TS and Python) — current mechanism is window-ceiling only, not a boolean; worth a correction pass on that decision.
