# T01 findings — Goose's step and provider layer, read in source

## 1. Crate layout relevant to the step

SURVEY.md's "4 crates" table is stale — the repo has since split provider concerns out of the monolithic `goose` crate:

- `crates/goose/src/agents/agent.rs` (6031 lines) — the step loop (`Agent::reply` → `reply_impl` → `reply_internal`)
- `crates/goose/src/agents/reply_parts.rs` (2198 lines) — request assembly, provider invocation, retry wrapper, chunk merging
- `crates/goose/src/context_mgmt/mod.rs` (1233 lines) — goose-specific glue over the context-management primitives (thresholds, tool-pair summarization, wiring to `Provider`)
- `crates/goose-context-management/` (new crate, 5 files) — the summarization/compaction algorithm itself, provider-agnostic
- `crates/goose-provider-types/src/base.rs` — the `Provider` trait and `MessageStream` type (the old `crates/goose/src/providers/base.rs` is now a thin re-export, lines 1-61)
- `crates/goose-providers/` (new crate) — the concrete per-vendor adapters (anthropic, openai, google, databricks, ollama…); `crates/goose/src/providers/` now holds mostly CLI-wrapper/ACP adapters (claude_code.rs, gemini_cli.rs, codex.rs) and provider-registry glue
- `crates/goose-agent/src/events.rs` — `AgentEvent`, the harness-level semantic event type

## 2. The step, walked end to end

`Agent::reply_impl` (`agent.rs:1921`) checks `check_if_compaction_needed` once, before the step loop starts (`agent.rs:2179-2185`), and runs full-history compaction inline if the threshold is already exceeded when the turn begins (`agent.rs:2196-2258`). It then calls `reply_internal` (`agent.rs:2269`), the actual step loop (`async_stream::try_stream!` block from `agent.rs:2394`):

1. **Drain steering / cancellation** — check `cancel_token` (`agent.rs:2440`), drain a pending-steers queue (`agent.rs:2444-2469`).
2. **Turn-context injection** — `moim::turn_context_message` appends a small system-authored message (turn number, compaction info) before the request (`agent.rs:2418-2435`).
3. **Request construction** — `stream_response_from_provider(provider, model_config, session_id, &system_prompt, conversation.messages(), &tools, &toolshim_tools)` (`agent.rs:2532-2540`).
4. **Streaming + chunk merging** — inside `stream_response_from_provider` (`reply_parts.rs:331-573`): retries a stream that errors before its first item (`reply_parts.rs:403-461`, transient-only, provider-supplied `RetryConfig`), then forwards `(Option<Message>, Option<ProviderUsage>)` chunks, coalescing consecutive text/thinking deltas and assigning a stable message id to mergeable assistant chunks (`reply_parts.rs:550-565`).
5. **Chunk-to-event translation** — the step-loop consumer (`agent.rs:2579-3384`) turns each `(Message, ProviderUsage)` chunk into `AgentEvent::Message` / `AgentEvent::Usage`, tracks whether the turn produced content, called tools, hit an output-token-limit flag on `MessageMetadata`, or returned a `ProviderError` (rate limit, `ContextLengthExceeded`, refusal, …).
6. **Termination handling** — no raw wire `stop_reason` crosses into this loop at all (see §3). Termination is structural: absence of `ToolRequest` content in the final assembled `Message` ends the turn (subject to an empty-turn retry policy); presence routes to tool dispatch and the loop repeats; `turns_taken > max_turns` breaks with a canned message (`agent.rs:2526-2530`); `ProviderError::ContextLengthExceeded` triggers reactive recovery-compaction, capped at 2 attempts (`agent.rs:3078-3131`).
7. **Tool dispatch → admit results** — categorize tool requests, run approved/pre-approved tools, permission-check the rest (`agent.rs:909-1000`; not traced further, out of scope for this ticket).

## 3. The provider trait — full interface

`Provider` (`crates/goose-provider-types/src/base.rs:478-725`), `#[async_trait]`, `Send + Sync`:

- **Required:** `get_name() -> &str`; `async fn stream(&self, model_config: &ModelConfig, system: &str, messages: &[Message], tools: &[Tool]) -> Result<MessageStream, ProviderError>` (`base.rs:492-499`) — the only method every adapter must implement.
- **`MessageStream`** (`base.rs:341-343`): `Pin<Box<dyn Stream<Item = Result<(Option<Message>, Option<ProviderUsage>), ProviderError>> + Send>>`. A chunk carries a fully-formed (possibly partial-text) `Message`, never a raw wire delta — chunk-to-`Message` translation happens inside the adapter, before this seam.
- **Defaulted (overridable):** `complete()` — collects the stream via `collect_stream` (`base.rs:380-471`, coalesces text/thinking blocks respecting signature and audience rules; unit-tested exhaustively, `base.rs:900-1021`); `get_context_limit()`; `retry_config() -> RetryConfig`; `fetch_supported_models` / `fetch_supported_model_info` / `fetch_recommended_models` (canonical-registry filtering, `base.rs:550-624`); `map_to_canonical_model`; `manages_own_context() -> bool` (default `false`, `base.rs:645-647`); `supports_builtin_tools()`; `configure_oauth` / `refresh_credentials`; `update_mode`; `thinking_effort_support` / `subscribe_thinking_effort_support` / `set_thinking_effort`; `apply_model_selection`; `permission_routing` / `handle_permission_confirmation`; `resume(session_id)`; `provider_session_id()`.
- **Error type:** `ProviderError` (`crates/goose-provider-types/src/errors.rs:8-60`), 13 variants — `NotConfigured`, `Authentication`, `ContextLengthExceeded`, `RateLimitExceeded{details, retry_delay}`, `ServerError`, `NetworkError`, `RequestFailed`, `InvalidValue`, `ExecutionError`, `UsageError`, `NotImplemented`, `EndpointNotFound`, `CreditsExhausted{details, top_up_url}`, `Refusal{details, category}`. No `StopReason`/`FinishReason` variant or type anywhere in this crate.
- **Config surface:** a separate `ProviderDef` trait (`crates/goose/src/providers/base.rs:31-61`) — `from_env` / `from_env_with_working_dir` / `from_env_with_default_model` — construction-time, not the streaming trait.
- **Invariant the caller must know but the trait doesn't type-enforce:** `manages_own_context()` is read by the *caller* at two sites — `check_if_compaction_needed` returns `false` unconditionally when true (`context_mgmt/mod.rs:231-233`), and the stream-wrapper's retry-on-first-error loop is skipped entirely when true (`reply_parts.rs:404`). A provider reporting `manages_own_context() == true` opts its caller out of goose-side context management altogether — a capability flag read across the seam, not a parameter of `stream()`.

## 4. Who owns request construction; where the window is assembled; context-management hooks

**Request construction is harness-owned, not provider-owned.** `Agent::prepare_tools_and_prompt` (`reply_parts.rs:187-231`) builds `system_prompt` and the tool list from extension metadata, hints, and mode. `stream_response_from_provider` (`reply_parts.rs:331-401`) projects the conversation to `agent_visible_messages()`, runs `fix_conversation` (protocol repair — orphaned tool_use/tool_result pairing) and `merge_consecutive_messages_for_request`, and only then calls `provider.stream(model_config, system, messages, tools)`. The adapter receives an already-assembled, already-repaired `&[Message]` slice; its only jobs are wire-format translation and chunk emission. This answers SURVEY's provider↔assembler seam question cleanly: **the assembler (harness) owns it; the adapter is a pure translation module** — exactly the shape SURVEY §3's "copy behind an interface you wrote" rule wants.

**The window is assembled before the loop, not per-step.** `Agent::prepare_reply_context` (`agent.rs:856-907`) takes an already-loaded `Conversation` and runs `fix_conversation` plus computes `tool_call_cut_off`; it does **not** truncate. The `conversation: Conversation` value is a local mutable variable threaded through the entire step loop, pushed onto with each turn's messages (`persist_and_push_message_with_id`, e.g. `agent.rs:2460-2467`) and re-read whole on every `stream_response_from_provider` call (`agent.rs:2537`). There is no separate assembler module distinct from the loop — window state lives in the loop's local variable.

**Context management: two distinct mechanisms, same underlying primitive.**

1. **Full-history compaction** (`compact_messages`, `context_mgmt/mod.rs:70-207`) — threshold-gated (`check_if_compaction_needed`, `usage_ratio > threshold`, default from `goose_context_management::DEFAULT_COMPACTION_THRESHOLD`), checked once per turn before the loop starts (`agent.rs:2179`) and reactively on `ProviderError::ContextLengthExceeded` mid-loop, capped at 2 attempts (`agent.rs:3078-3131`). Mechanically: every existing message gets `.with_metadata(...with_agent_invisible())` (`context_mgmt/mod.rs:143-146`), a single LLM-generated summary message is appended agent-visible, and (for auto-compact) the most recent user text message is re-appended after it (`context_mgmt/mod.rs:169-172`). Emits `AgentEvent::HistoryReplaced(conversation)` (`agent.rs:2239`) — the event carries the full new `Conversation`, not a diff.
2. **Tool-pair summarization** (`maybe_summarize_tool_pairs`, `context_mgmt/mod.rs:495-524`) — count-gated (`tool_ids_to_summarize`, `context_mgmt/mod.rs:379-410`: fires once eligible tool-call count exceeds `tool_call_cut_off`, batches 10 at a time, always protects the current turn's own tool calls), fired every step as a **background `tokio::spawn` task** that does not block the in-flight request (`agent.rs:2549-2560`), awaited and applied only after the current stream finishes (`agent.rs:3392-3420`). Same primitive as (1) at message-pair granularity: the tool_request/tool_response pair gets `.with_agent_invisible()` (`agent.rs:3410-3413`), and a one-line LLM summary of that pair is appended at the tail (`agent.rs:3414`), not spliced back into its original position.

Both mechanisms are storage-append-only — no message is ever physically deleted, only flagged (`MessageMetadata::agent_only()` / `.with_agent_invisible()`, `crates/goose-provider-types/src/conversation/message.rs:845,872`) — but `Conversation::agent_visible_messages()` (`crates/goose-provider-types/src/conversation.rs:178`) is what request construction filters through (`reply_parts.rs:343`), so the **message sequence actually sent to the provider** changes shape after either mechanism fires: a tool pair vanishes from the middle, a summary appears at the tail. That is a mid-sequence content change from the provider's-eye view regardless of what storage does underneath.

## 5. Mismatches with POSITION.md / SURVEY.md

- **"Goose's memory is just another MCP extension, so it cannot teach the memory-provider seam"** (POSITION §4) is true of long-term memory, but a second, unnamed memory-adjacent mechanism exists inside Goose itself: **window-level context management**, which is not an extension — it is harness-core code (`crates/goose/src/context_mgmt/`, `crates/goose-context-management/`) sitting directly in the step loop. SURVEY §3's donation table ("streaming, provider trait, MCP client lifecycle, tool dispatch, session store, subagent spawn") undercounts what exists to lift — compaction plumbing and the threshold/cutoff arithmetic are real, working, and provider-agnostic (`goose-context-management` has no `goose` dependency in its core `summarize`/`structured` modules).
- **Tool-pair summarization *is* the splice operation POSITION's op-set excludes.** §6 question 2 rules append + rewind, "splice is not built," on cache-mechanics grounds. Goose ships exactly this operation, by default (`tool_pair_summarization_enabled()` defaults to `true`, `context_mgmt/mod.rs:27-31`), running continuously per-step rather than rare-and-batched, to solve the same problem POSITION names as splice's motivating case — bulky output admitted verbatim — but as post-hoc eviction of already-admitted content rather than admission-time deferral. The source shows the policy is real and default-on; it does not show whether it is cheap under prefix caching.
- **Partial corroboration of §6 question 7.** Goose's `with_agent_invisible()` pattern is independently-arrived-at evidence for removal-as-demotion — nothing is deleted from the session store, only flagged invisible, with `session_manager.update_message_metadata` available to restore it. A positive precedent, not a mismatch.
- **The provider trait does not donate cleanly.** `manages_own_context()` (`base.rs:645-647`) is a capability flag the trait author must implement and the *caller* must branch on at two separate call sites to decide whether context management and stream-retry run at all. The interface is not a pure `(system, messages, tools) → stream` function; it carries a policy-relevant escape hatch that leaks a provider-side property (does this adapter wrap a stateful CLI tool with its own history?) into harness-side control flow.
- **SURVEY §1's seven-`stop_reason` termination table does not describe what crosses Goose's provider↔harness seam.** No `StopReason` type exists in `goose-provider-types`; each adapter absorbs the wire-level completion signal internally, and the loop's termination decision reduces to two structural questions on the assembled `Message` (does it carry `ToolRequest` content; does `MessageMetadata` carry `output_token_limit_reached`) plus the `ProviderError` channel. Goose's own ACP server reconstructs a three-value `StopReason` (`Cancelled`/`MaxTokens`/`EndTurn`, `crates/goose/src/acp/server.rs:667-674`) purely from harness-side booleans — the seven-value richness is real at the wire level and collapsed well before it would reach an arx-side loop built this way.

## 6. Decision questions this exposes

- Does arx's provider trait carry anything like `manages_own_context()` — a capability flag the assembler must branch on — or is that shape (a CLI-wrapped provider with its own history) out of scope for arx entirely?
- Goose's chunk type is `(Option<Message>, Option<ProviderUsage>)`, a semantically complete unit per chunk, not a raw wire delta. Does arx's provider↔harness seam want the same shape, or does raw-delta-plus-harness-side-assembly belong on arx's side of the line?
- Given termination in Goose is "does the assembled Message contain a tool request," does arx's assembler need a distinct termination signal at all — and if so, does that inspection happen provider-side (translating wire stop_reason) or assembler-side (reading the Message)?
- Tool-pair summarization is evidence that mid-window drop is a real, default-on, continuously-firing mechanism in a production harness. Does that change arx's answer on when splice earns its keep, or does the mono-task window premise (§6 q2) rule out the case Goose's mechanism exists to handle?
- Goose's compaction primitive is "flag invisible, append summary" at two granularities (whole-history, single tool pair) under two triggers (turn-start threshold, per-step count). Is one primitive at two granularities the right shape for arx's `Keep`/`Fold`/`Drop`/`Admit` plan, or does conflating when-to-fire with what-to-demote reproduce the coupling question 6 already flags?
- Goose checks full-history compaction once per *turn* plus reactively on error — not once per *step*. Does arx's "pressure check + window assembly" line want per-turn or per-step cadence, and does that change what "armed on pressure, fired at a seam" means operationally?
- Goose's `agent_invisible` flag splits durable store from request-time projection. Does arx want the same two-layer split, and if so, does the projection step become part of the assembler's interface or a separate stage?

## Unknowns and confidence

Tool dispatch, permission checking, and MCP client lifecycle were read only far enough to place them in the step. The wire-level parser consuming `stop_reason` inside a concrete adapter was not traced line-by-line — the trait-boundary evidence answers what crosses the seam, not every adapter's internals. `goose-cli`'s consumption of `AgentEvent` was not read.

Confidence: high on request-construction ownership, the provider trait surface, and the two context-management mechanisms (directly read, cross-checked with call sites). Medium on the termination-abstraction claim and on the cache cost of tool-pair summarization (mechanism verified in source; cache cost inferred from prefix-caching mechanics, not measured).
