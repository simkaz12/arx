## 2. Session representation, persistence, resume

`Session` (`session_manager.rs:61-97`) — id, working_dir, name, `SessionType` (`User | Scheduled | SubAgent | Hidden | Terminal | Gateway | Acp`, lines 46-55), timestamps, `ExtensionData`, token usage (current + accumulated), cost, `recipe`, `conversation: Option<Conversation>`, `provider_name`, `model_config`, `goose_mode`, `archived_at`, `project_id`, `parent_session_id`.

Persistence is SQLite (`sqlx::sqlite`, `SESSIONS_FOLDER`/`DB_NAME = "sessions.db"`, lines 27-29), schema version 16, migrated in-code via `ALTER TABLE`/`CREATE TABLE IF NOT EXISTS` under `BEGIN IMMEDIATE` (`session_manager.rs:947-1089`, migration ladder `1270-1552`). Three tables: `sessions` (metadata, no message body — `980-1010`), `messages` (normalized rows: `session_id`, `role`, `content_json`, `message_id`, `metadata_json` — `1018-1029`), `usage_ledger` (per-turn cost/token rows, `1036-1050`). `parent_session_id` is an indexed FK (`idx_sessions_parent`, line 1076) added in a later migration (`1514-1518`) — the schema was retrofitted for subagent lineage, not designed in from the start.

Resume is not a session-object checkpoint — no `Agent` struct is serialized. `AgentManager` (`execution/manager.rs:33-47`) holds an LRU cache (`sessions: RwLock<LruCache<String, Arc<Agent>>>`, default capacity 100, `DEFAULT_MAX_SESSION` line 16) of *live* agent processes keyed by session id. On a cache miss, `create_agent_locked` (`manager.rs:169-288`) rebuilds the `Agent` from the SQLite row: restores provider from `session.provider_name` (`restore_provider_from_session`, line 217), reloads extensions (`load_extensions_from_session`, line 228), reapplies recipe response schema (`229-233`), then falls back to the process-global default provider if the session had none (`236-258`). Per-session creation locks (`creation_locks`, comment at `38-46`) serialize concurrent resume attempts so two callers racing on the same session id don't double-initialize. Conversation/messages load separately by session id when a reply actually runs; the `messages` table is the source of truth. So: durable state = SQLite rows; resume = rehydrate-on-demand; the live `Agent` is a cache entry, evictable under LRU pressure.

## 3. Subagent spawn, supervision, isolation — and what happens to a finished subagent's context

Spawn is an MCP tool call. `summon` (`platform_extensions/mod.rs:120-131`, `summon.rs:37`) is registered in `PLATFORM_EXTENSIONS` (`platform_extensions/mod.rs:29-227`) as a `McpClientTrait` implementor exactly like `todo`, `developer`, `chatrecall` (Goose's own memory-recall extension) and `orchestrator` — same registry, same trait, same in-process-but-tool-shaped seam. `SummonClient::call_tool` dispatches `"delegate"` and `"load"` (`summon.rs:2086-2127`); a subagent cannot itself call `delegate` — `handle_delegate` refuses at `summon.rs:1349-1351` if the calling session's own type is already `SubAgent` ("Delegated tasks cannot spawn further delegations"), so recursion depth is capped at one level by a runtime type check, not the type system.

Every delegated task gets its own first-class `Session` row: `create_subagent_session` (`summon.rs:570-598`) calls `SessionManager::create_session(..., SessionType::SubAgent, ...)` and sets `parent_session_id` when a parent id is known. `run_subagent_task` → `get_agent_messages` (`subagent_handler.rs:47-239`) constructs a fresh `Agent` (`Agent::with_config`, line 140), builds a subagent system prompt (`build_subagent_prompt`, `241-270`, template `subagent_system.md`), then calls the *same* `agent.reply(...)` used by top-level sessions (`193-200`) scoped to the subagent's own session id — the subagent's transcript is written through the ordinary session/message persistence path, not held only in memory. `AgentConfig::is_subagent = true` and mode is forced to `GooseMode::Auto` (comment `summon.rs:1973-1975`: any approval-requiring mode would hang on the subagent's own confirmation channel, since `get_agent_messages` doesn't forward `ActionRequired` to the parent).

What returns to the parent is not the transcript — `extract_response_text` (`subagent_handler.rs:64-117`) pulls only the last message's text (`return_last_only: true` at both call sites, `summon.rs:2015`, `1397`) or, if the delegate declared a response schema, `get_final_output`'s structured value (`272-283`). Sync mode returns this directly as the tool result (`summon.rs:1419-1428`). Async mode stores it in an in-process `CompletedTask` (`summon.rs:79-87`, populated in `cleanup_completed_tasks`, `1879-1929`) retained only for a TTL (`completed_task_ttl()`) and consumed once by `load` unless `peek: true` (`handle_load_task_result`, `1007-1065`; removal at line 1031, `completed.remove(task_id)`).

That ephemeral report channel is the only place Goose narrows the subagent's context. **The underlying session row and its full message history are not discarded** — they persist in the same `sessions`/`messages` tables as any user session, durable until an explicit `delete_session` call (`session_manager.rs:470`, `2097`, `4588`; no automatic sweep of `SubAgent`-typed rows found). They're excluded from default listings by a `session_type` filter (`list_sessions_by_types`, `session_manager.rs:455`), reachable by `parent_session_id`, and directly viewable — `orchestrator`'s `view_session` tool (`orchestrator.rs:72-79`, params `session_id`, `mode: "first_last" | "summarize"`) reads a named session's conversation on demand, functionally an audit-the-material-when-the-report-smells-wrong operation. But there is no distinct evidence tier: a subagent session is an ordinary, fully-assertable `Session` row, just type-filtered out of the default view — nothing marks it "material, never retrievable as an assertion," nothing tracks provenance-plus-sha, nothing prevents it being read straight back into a window as fact.

## 4. Cancellation and abort propagation

Two independent registries, not one.

**Per-session (foreground/sync):** `AgentManager.cancel_tokens: HashMap<String, CancellationToken>` (`execution/manager.rs:37`). `try_register_cancel_token` errors "Session is currently busy" if a token is already registered for that id (`352-363`) — one live operation per session id. `cancel_session(session_id)` calls `token.cancel()` (`371-378`). The token is threaded from `agent.reply()` down through `dispatch_tool_call` (`agent.rs:1179-1295`, `cancellation_token.unwrap_or_default()` at 1293) into `extension_manager.dispatch_tool_call`, so an in-flight *tool call* — including a synchronous subagent delegation — observes the same cancellation. Inside the streaming loop, cancellation is a `tokio::select!` race against `stream.next()` (`agent.rs:2579-2588`: `_ = cancel_token.cancelled() => break`) — it can interrupt mid-token-stream, not just at a step boundary. `orchestrator::CancelTokenGuard` (`orchestrator.rs:29-59`) unregisters the token on `Drop`, including on panic, so a killed task doesn't leave a phantom "busy" session.

Sync-mode delegation passes the *parent's own tool-call token straight through* (`summon.rs:1399`) — cancelling the parent turn cancels the sync subagent for free, no derivation.

**Background tasks are a separate lane.** Async delegation mints an unregistered `CancellationToken::new()` (`summon.rs:2004`) held only in `SummonClient`'s own `background_tasks: HashMap<String, BackgroundTask>` — never entered into `AgentManager.cancel_tokens`. It survives parent-turn/session cancellation and is reachable only through `summon`'s own `load(..., cancel: true)` (`summon.rs:1105-1126`): cancel the token, then race the task's `JoinHandle` against a 5-second grace timer before force-`handle.abort()` (`1117-1126`). So `orchestrator`'s generic `cancel_session(subagent_session_id)` cannot stop a backgrounded subagent — the two supervision surfaces don't cross-reference.

Goose has no harness-owned subagent seam distinct from its tool-dispatch seam; spawning a subagent is, structurally, calling a tool.

## 6. Decision questions this exposes

- Decision `061d7942` makes traces a distinct non-assertable evidence class with provenance+sha. Goose's subagent session is an ordinary, fully-assertable session row filtered out of default listing by type. Does arx's trace archive live *inside* the same session store as ordinary sessions (Goose's shape, with a stricter read-path gate on top), or in a structurally separate store the harness never lets recall/grounding reach by construction?
- Goose caps delegation depth by a runtime type check on the calling session. Does arx want recursion depth as a type-level property of the subagent↔trace-archival seam, given `eeedd9fe`'s stated reason for choosing Rust was making illegal states compile errors?
- Two disjoint cancellation registries exist, and a background subagent is invisible to the generic supervisor. Does arx's subagent supervision need one registry by construction, or is the foreground/background split itself worth keeping and naming as two seams (echoing question 6's admission-vs-eviction shape)?
- Goose returns only last-message text (or a schema'd final output) and separately exposes `view_session` for the full transcript. Is arx's verdict-vs-trace split satisfied by that shape, or does "never retrievable as an assertion" require the read path itself — not just the default listing filter — to refuse to hand back trace content as fact?
- `parent_session_id` was retrofitted in a later migration. If arx's session/trace schema is Goose-derived, does the harness need parent-child lineage from schema v1, or is retrofit acceptable given SQLite's `ALTER TABLE` migration story already works here?
- Sync-mode subagent cancellation reuses the parent's literal `CancellationToken` (no `.child_token()` derivation). Does arx want a genuine parent→child cancellation tree (so a subagent's own cancellation doesn't reach back up), or is token-sharing the correct default for the ladder's delegate tier?
- The subagent's own `ActionRequired` channel is not forwarded to the parent, which is why Goose forces subagents to `GooseMode::Auto` — a supervision gap acknowledged in a code comment. Does arx's subagent seam need a first-class permission-escalation path from child to parent, given the daily-driver posture cares about approval gates?
