# T04 findings — steering-queue semantics as the field actually builds them

Ticket: [T04](../T04-steering-field.md) · resolved 2026-08-24 · produced by a hand-ex research agent from Goose source (commit `8d844eecbdfd65626a881c9e8784ae8dc6093f1d`), first-party issue trackers via `gh`, official Claude Code docs, and the local transcript corpus.

**Answer, up front.** SURVEY §1's three-way "steer / queue / abort" table is a real proposal in the field, not an invented convenience — it is opencode issue #32157, filed 2026-06-13, still open and unimplemented. But it is a proposal against the field's actual convention, which is a **two-way** split: an immediate-boundary inject (steer/asap) and a hold-to-idle follow-up (queue/when_idle). Every shipping system checked lands on the two-way split or less. "Abort" is never a third delivery mode alongside them — it is an orthogonal run-control action, and what abort does to a *pending, not-yet-delivered* queue is precisely where the field disagrees and where the open bugs live.

## 1. Per-system mechanism, drain point, chosen boundary

**Goose.** One `SteerQueue` (`Arc<Mutex<VecDeque<Message>>>`) per session, drained by `SteerOperation`, first in the state-machine's operation list — literally the top of the step. Boundary is `between_turns = ends_turn(messages) || last_effective_role(messages) == Tool` (`crates/goose/src/agents/state_machine/ops_steer.rs:48-53`). That is coarser than "next tool call": it is *after the whole current model turn's tool calls resolve*. Confirmed by test `steering_is_fifo_during_inference_and_survives_compaction` (`.../tests/steering_lifecycle.rs:9-76`): two steer messages sent mid-inference queue FIFO and both land in the *next* model call together; a steer sent near the context limit survives being folded into the compaction request itself. Abort is not a delivery mode — `discard_pending_steers()` (`agent.rs:579-581`) is called only from `clear_active_run` (full run teardown, `acp/server.rs:1789`) and `/new` (`goose-cli/.../session/mod.rs:1185`). Plain cancellation (`CancellationToken`) does **not** clear the queue — test `cancellation_preserves_queued_steering_for_resume` (`.../tests/steering_lifecycle.rs:78-124`) shows a cancelled run's steer survives and fires on resume. So Goose has three states, but not SURVEY's three: **deliver-at-boundary**, **cancel-and-preserve**, **discard-on-teardown**.

**pydantic-ai-harness / pydantic-ai core.** Issue #89 ("Message Delivery Queues," closed 2026-07-13 via pydantic-ai PR #4980, citing pi-mono's `steer()`/`followUp()` as the design source) shipped exactly two priorities on `AgentRun.enqueue(content, priority='asap'|'when_idle')`: `asap` drains at the next `ModelRequestNode` — after the current step's model response and tool returns, per-step, not per-turn — and `when_idle` drains only when the run would otherwise end. No third priority. Issue #307 (open, 2026-06-25) is the unclosed gap: `enqueue` must run on the live `AgentRun`'s own event loop, so a served/web agent (`to_web`/`dispatch_request`, one-shot per HTTP request) has no cross-request handle to steer or cancel a turn a prior request started — the queue exists but is inaccessible from outside the process that owns the loop.

**anomalyco/opencode.** #32157 is the field's clearest three-way *proposal* — `queue` (full next task, normal compaction boundary), `steer` (inline control context for the active turn, must not create its own compaction unit, injected before the next model call or after the current tool call completes), `break` (explicit rename of interrupt/abort). Unimplemented as of Aug 2026. What ships is narrower and regressing: #44108 (open) reports the web UI is steer-only since the queue setting was removed. Separately, PR #32425 (open) implements a **different** steer/cancel/abort triad at the subagent-supervision axis, not the incoming-message axis — a parent controls a running child with `task_steer` (inject `<steer>`, child adapts and continues), `task_cancel` (soft, turn-boundary-respecting — a child mid-tool-call only breaks once that tool returns), `task_abort` (hard, immediate, no grace window). A genuinely different, useful cut: **soft-stop vs hard-stop** as two force levels, distinct from redirect. SURVEY's single "abort" bucket collapses a distinction opencode's own PR treats as load-bearing.

**HAPI** (`tiann/hapi`, a multi-backend session wrapper over Codex/Claude Code/Cursor/Pi) is the field's own comparative study. Issue #888 (closed, empirically verified against `codex 0.139.0` and `claude 2.1.175`) found the backends **asymmetric at the protocol level**: Codex's app-server exposes a first-class, non-interrupting `turn/steer` RPC (`expectedTurnId` precondition, rejects on `review`/`compact` turns as `NonSteerableTurnKind`) — true mid-turn steering. Claude has **no such primitive** in `--input-format stream-json` — the author injected a stdin message ~2.0s into a running turn and it was silently ignored; the turn ran to completion never acknowledging it, and no follow-up turn answered it. The only approximation with Claude is `interrupt` + resubmit, destructive to the in-flight step. Issue #1466 (closed 2026-08-11) shows HAPI's own agent flavor "pi" was rolled back from automatic immediate-steer to explicit-opt-in-queue, to match the majority convention: "All other flavors default to `queue`" — Codex, Claude, and Cursor all default to hold-to-idle in HAPI's wrapper, with steer as an opt-in per-message promotion (PR #1443).

**Claude Code itself**, per its own tracker and docs. `code.claude.com/docs/en/how-claude-code-works#interrupt-and-steer` (fetched 2026-08-24): "Type a correction and press Enter to send it without stopping the running tool. Claude reads it as soon as the current action completes and adjusts before deciding its next step" — the steer/asap boundary, at tool-call granularity. Separately: "Press Esc to stop Claude immediately... If you have messages queued, Claude Code sends them next." **Esc does not clear the queue** — directly contradicting SURVEY's "abort: drop the current run, clear the queue, start fresh." There is no native end-of-turn-only queue mode; #63190 ("Deferred Messages — Queue Input for End of Turn," filed 2026-05-28) is still **open** with comments through 2026-08-20, repeatedly citing Codex's queue/steer toggle as the wanted reference UX. #30492 ("Real-time steering... non-destructive channel distinct from Esc") was closed COMPLETED 2026-08-17 by an Anthropic engineer pointing at the docs section above — but the thread's last comment (2026-08-14) is unsatisfied, asking for Codex's explicit Queue-vs-Steer toggle; the field's own users do not agree the shipped default resolves the request. #49373 (closed) documents drift: the flush point moved from "any LLM pause, including mid-task tool-call pauses" to a tighter tool-call-boundary definition between April and August 2026 (self-reported by a commenter who built and then retired a `PreToolUse` hook workaround, comment dated 2026-08-11).

## 2. Failure reports and open disputes

- **opencode #40955** (open, 2026-08-07, `packages/opencode/src/session/prompt.ts`, `SessionPrompt.cancel`): queued-but-undelivered follow-ups are **silently and permanently dropped** when the active turn is interrupted. Root cause named in the issue: `onAbort` sets `followup.paused[id] = true` with no unpause path. The messages persist in SQLite as `user` rows, timestamped up to 18 minutes before the abort, never answered — from the UI, the `QUEUED` tag simply vanishes.
- **opencode #33812** (open, filed six weeks earlier, same root cause) — filed independently, not yet merged into #40955 despite the bot flagging overlap with #40645.
- **opencode #40645** (open): ESC interrupt not taking effect immediately; queued messages keep firing alternately — an ordering race between interrupt processing and queue drain.
- The three together show opencode's **stated** intent (abort should preserve the queue, matching Claude Code's docs and Goose's soft-cancel) is right, and the shipped implementation inverts it, open across two independent filings spanning two months.
- **pydantic-ai-harness #307** (open): the enqueue mechanism exists in core but is unreachable for a served agent — a structural gap between "the primitive exists" and "the primitive is reachable from where a real request comes from."
- **anthropics/claude-code #63190** (open): no native defer-to-end-of-turn mode, accumulated +1s through 2026-08-20, explicitly modeled on Codex's UX.
- **anthropics/claude-code #30492** (closed as completed, contested in its own thread — the closing answer and the ask talk past each other on whether steer-without-a-queue-toggle is what was requested).

## 3. Claude Code's observed behaviour, from the local transcript corpus

The `.jsonl` schema carries a `queue-operation` entry type with `operation: enqueue` / `remove` (some sessions use `dequeue` for a separate, content-less housekeeping signal — a corpus-mining gotcha: matching by operation name alone silently pairs the wrong events; match by message content). Two clean examples of a user-typed message enqueued while a tool call was in flight, matched to its `remove`:

- `~/.claude/projects/-home-user-Projects-Tabularium/b67588d1-5cdc-492d-8bd5-0ae2156bbaf4.jsonl`, line 83 (`enqueue`, `2026-08-01T14:18:38.863Z`, 18.9s after the preceding `tool_use`), content "make a .sh in root of tabularium in a similar way as pi-assistant has for deployment", matched to line 85 (`remove`, 75.6s later) — the drain sits immediately after the single intervening `user:tool_result` at line 84, before the next `assistant:thinking` at line 91.
- `~/.claude/projects/-home-user-Projects-client-b-be/771199f8-15d1-4e34-ade7-4fe43d8ff613.jsonl`, line 419 (`enqueue`, 10.4s into a tool call) matched to line 422 (`remove`, 5.1s later).

Both land right after the in-flight tool call's result, before the next model call — corroborating the docs' "as soon as the current action completes" and matching the tool-call granularity pydantic-ai's `ModelRequestNode` boundary describes, not Goose's coarser end-of-turn boundary. No genuine Esc-abort example surfaced in the sampled corpus (~80 largest transcripts; "interrupted"/"cancelled by user" hits were substring noise inside unrelated tool output). An absence, not a finding — real-work sessions, not synthetic interrupt tests.

## 4. Mismatches with SURVEY §1

- The three-way steer/queue/abort framing exists as a named field proposal (opencode #32157) but not as converged, shipped behaviour anywhere checked. What ships is a two-way split; "abort" is a control action, never a delivery mode a message is assigned to.
- SURVEY's abort row ("drop the current run, clear the queue, start fresh") is contradicted by the majority stated intent: Claude Code's docs, opencode's intended design, and Goose's soft-cancel path all preserve the pending queue on abort. Where systems actually clear it, that is either a deliberate second, harder action (Goose's `discard_pending_steers`, fired only at session teardown) or an acknowledged open bug (opencode #40955, #33812) — never the stated behaviour of abort as such.
- The "safe boundary" is not one universal point. Goose drains once per full model turn (all tool calls resolved). pydantic-ai core and the observed Claude Code corpus drain per step (after the current tool call's result, before the next model call) — materially tighter. Both get described with nearly identical prose ("at the next safe point" / "as soon as the current action completes"): the words used field-wide do not disambiguate turn-granularity from step-granularity, and that gap is exactly the axis #32157 tries to make configurable.

## 5. Decision questions for arx's steering↔step-boundary seam

- Is arx's admission ladder the same seam as steering delivery, or a second seam that happens to share the word "boundary" — given POSITION §6 already separates "harness owns validity" from "memory owns value," where does a steer message's *delivery timing* sit relative to that split?
- Does arx need Goose's three states (deliver, cancel-preserve, discard-on-teardown) or pydantic's two (asap/when_idle) — and if two, does arx's mono-task window (no splice, `Keep`-contiguous) make "queue to end of task" cheaper or more expensive than in a multi-turn, splice-capable harness?
- opencode #32157's compaction argument — a steer message must not become its own compaction unit, must stay attached to the task it modified — how does that interact with arx's rewind-residue rule (write → cut → append)? Is a steer message something a rewind could orphan mid-flight, and if so what does its residue look like?
- Given HAPI's finding that steer is not universally implementable (Claude Code's stdin has no non-destructive mid-turn primitive at the protocol layer, only at the harness's own queue layer) — does arx's single-process shell make this a non-issue, or does it just move the same asymmetry into "does arx's step loop check the queue between every tool call, or only between full turns"?
- Should abort's effect on the pending queue be a named, explicit choice in arx (as Goose makes it, with two different verbs) rather than an implicit side effect discovered by testing — given that is precisely where three of the five systems checked have open bugs or disputes?
- Does arx want steer-message provenance markers (opencode's "⊘ Steered/Cancelled/Aborted by user/by parent," visible in the transcript) as part of the never-assertable evidence class `061d7942` defines for traces, or is a steer message a different durability class — closer to a fact, since it is content the model must act on, not evidence about what happened?

No genuine Esc-abort example in the sampled corpus. Goose's coarser per-turn (not per-tool-call) drain point is confirmed by its passing test, not merely undocumented.

Confidence: high on mechanism/drain-point claims (traced to source, docs, or first-party issue bodies). Medium on the "field convergence is two-way not three-way" generalization — five systems is a real but small sample, and opencode's proposal, if shipped, would change the count.
